# Diet Coach — trust audit + phased plan

> **Why this doc exists.** Every calorie figure in ZIVO originates from a language model,
> and until Phase 0 nothing downstream checked it. This is the audit of that (read from the
> code on `version-1` @ `dec5058`, 2026-08-30), the target architecture, and the phase plan.
> **Findings are referenced by id (`T1`…`T15`) from `FEATURE.md`s, commit messages and the
> later phases — keep the ids stable.**
>
> Status: **Phases 0–5 landed** (2026-08-30). Phases 6–8 are not started.

---

## The verdict, unsoftened

The engineering *around* the model is good: writes are confirm-gated (ADR-003), costs are
ceilinged, tool output is fenced against prompt injection, the seams make everything
offline-testable, and the PDF importer is allowed to decline rather than fabricate a plan.
But every one of those guards protects the **write** path and the **cost** path. Before
Phase 0, none protected the **number** path.

The domain model is already the right shape (structured foods with quantities and units)
and the deterministic pattern already exists in miniature (`diet_format.dart`;
`coach_report.js`, written without a model call so it "can't hallucinate numbers"). This is
a build, not a rewrite — two missing layers (a food database, a validator) and one missing
entity (goal + targets).

## Findings

| id | Severity | Finding | Status |
|---|---|---|---|
| **T1** | Critical | **The daily target is a model guess rendered as fact.** The "target" is `dayCalories(day)` — the sum of item calories — and for an imported plan those were generated by Claude. The ring, kcal-left, macro bars and every coach sentence inherit it. | **Labelled** (Phase 0); fixed by Phases 2–4 |
| **T2** | Critical | **No nutrition data source exists.** No food DB, no nutrition API, no composition table. Nothing can answer "how many kcal in 200 g chicken" but the LLM. *The missing dependency.* | **Fixed** (Phase 2) |
| **T3** | Critical | **No goal, no targets, no body context.** Zero hits for goal/TDEE/BMR/deficit in the diet feature. The coach cannot know whether the user is cutting or gaining. | **Fixed** (Phase 1) |
| **T4** | Critical | **The model didn't know what day it was.** No date in the prompt or messages; `get_today` returned no date; `get_diet` returned `day: "Every day"`. | **Fixed** (Phase 0) |
| **T5** | High | **Client/server disagreed about "today".** The app writes `dayKey` from device-local time; the server computed it in UTC. A UTC+3 user got yesterday's entries between local 00:00 and 03:00. | **Fixed** (Phase 0) |
| **T6** | High | **"Consumed" is an assumption, not a measurement.** Ticking a meal credits its *planned* macros. There is no way to log a food; "I ate two eggs and 100 g rice" is unrepresentable. | **Fixed** (Phase 3) |
| **T7** | High | **The prompt licensed free-hand estimation** ("when you estimate calories or macros… give a sensible range"). | **Fixed** (Phase 0) |
| **T8** | High | **Zero output validation.** Nothing compares the reply to the state it read. | Open — Phase 7 |
| **T9** | High | **`mark_meal_eaten` wrote an unverified meal id.** `validate` only checked it was a string; a hallucinated id created an orphan `dietEntries` doc. | **Fixed** (Phase 0) |
| **T10** | Medium | **Truncation ate the diet payload first.** Tool results are cut at 6 000 chars from the end, and `get_today` serialized `diet` last. | **Fixed** (Phase 0) |
| **T11** | Medium | **Four tools for deleted features still shipped** (`get_tasks`, `get_schedule`, `get_university`, `search_notes` — ADR-004), four of them awaited inside `get_today`. | **Fixed** (Phase 0) |
| **T12** | Medium | **`estimated` was decorative and lossy** — a "~" on one screen, dropped from the AI payloads entirely, reset to false on re-add. | **Fixed** (Phase 0) for display + AI payloads; the re-add reset remains (Phase 2) |
| **T13** | Medium | **The same nutrition math exists twice**, Dart and JS, agreeing only by comment discipline. No test compares them. | **Fixed** (Phase 2 for the resolver + calculator, Phase 4 for the state builder and the day resolver) |
| **T14** | Medium | **Nothing validates nutrition values at any boundary** — no 4/4/9 plausibility check, and `firestore.rules` only required `days is list`. | Partly (Phase 0 tightened `dietEntries`); plan items remain — Phase 2 |
| **T15** | Medium | **The safety boundary is one prompt sentence.** No detection, no deterministic intercept, no test. | Partly (Phase 1 added a deterministic low-calorie floor on targets); the rest — Phase 7 |

## Target architecture

A number may only move **downward** through this stack, never sideways out of the model.
The LLM lives in layer 5 and reads layer 3; it never writes into layers 1–4.

```
1  Nutrition data      food catalog: per-100g reference values + source/confidence/state   [MISSING]
2  Calculator          pure nutritionFor(food, qty, unit) → kcal/P/C/F + provenance        [exists in miniature]
3  Diet state          goal · targets · consumed · remaining · deltas · date · quality      [MISSING]
4  Rules engine        deterministic typed CoachingFindings, each with its evidence         [MISSING]
5  AI coach            phrases the findings; states no number it wasn't given               [exists]
6  Advice validator    checks every claim against state; falls back to deterministic text   [MISSING]
7  UI                  target card, provenance markers, the "why" behind a recommendation   [mostly exists]
```

The payoff of layer 4 emitting a deterministic sentence: a validator rejection is never a
dead end. The user still gets the right answer, just in the engine's plainer voice — which
is what makes it safe to reject aggressively.

**Tool set to move to** (replacing raw plan dumps): `get_diet_state()`,
`get_diet_targets()`, `resolve_food(query, qty, unit, state)` → resolved | **ambiguous** |
**not found**, `calculate_meal_nutrition(items[])`, `log_food(items[])` (propose→confirm),
`get_diet_history(days)`, and `mark_meal_eaten` (kept, now verified).

The hard part is not the engineering — it is **food-database coverage**. A user whose
staples aren't in the catalog hits "not found" constantly, and the pressure to paper over
that with a model estimate will be immediate and constant. How the app behaves at that
boundary *is* the trust promise; decide it before Phase 2 starts.

## Phase 0 — what actually landed (2026-08-30)

No new dependencies, no schema migration. It does not make the numbers *right*; it stops
the app claiming they are.

- **The turn knows the date (T4).** `runAiTurn` appends an uncached `CONTEXT` system block
  — the user's local weekday, date and time — after the cached prompt, so it can change
  every turn without touching the cache breakpoint. Every tool payload also states the date
  it resolved.
- **"Today" is the user's today (T5).** The app sends `utcOffsetMinutes` + `timeZoneName`
  with each `aiChat` call (`clientClockFields`, no timezone package); `functions/ai/dates.js`
  takes an optional `offsetMinutes` on every helper and resolves day keys, weekday slots and
  day/week/month ranges in the user's zone. An implausible offset falls back to server-local
  and the CONTEXT block then says the date may be off — it never bluffs. The daily usage cap
  now resets at the user's midnight too.
- **The prompt forbids invented numbers (T7).** The estimation licence is replaced by a
  `NUMBERS` section: every figure about the user's data must come from a tool result in that
  turn; arithmetic on tool values is fine, inventing an input is not; and it states plainly
  that there is **no food database**, so an unlogged food gets an honest "I can't tell you
  that" rather than a hedged guess. `gateway.test.js` asserts this text survives.
- **A meal id is proven before it can be confirmed (T9).** Mutating tools may now declare an
  async `verify` hook, run at propose time, that checks the input against real stored data
  and patches the payload with what it found. `mark_meal_eaten` uses it to prove the id
  exists in the active plan, to resolve the `dayKey` in the user's zone, and to take the
  meal's **real label** from the plan rather than the one the model claimed. A bad id comes
  back as a tool error naming the ids that do exist. `applyProposedAction` re-checks at
  confirm time, because a proposal can wait an hour and the plan can change.
- **Truncation can't eat nutrition (T10).** `get_today` serializes `date` and `diet` before
  `workouts`.
- **The dead tools are gone (T11).** `get_tasks`/`get_schedule`/`get_university`/
  `search_notes` and their `store.js` readers are deleted.
- **Provenance is load-bearing (T12).** `estimated` now travels through `get_diet`/
  `get_today` per item *and* aggregated onto meal and day totals. On device,
  `anyEstimated`/`mealEstimated`/`dayEstimated`/`approx` live in `diet_format.dart`,
  `dietDaySummary` returns `kcalLeftEstimated`, and the "~" convention now covers the Diet
  hero number (whose label reads `EST. KCAL LEFT`), the planned-total caption, the macro
  bars, the meal rows, the plan reference card, Today's glance and the Hub tile.
- **`dietEntries` rules tightened (T14, partly).** `dayKey` must match `yyyy-MM-dd`,
  `mealId` must be non-empty and ≤ 200 chars, `date` must be a timestamp, and no unknown
  fields may be smuggled in. Rules can't join against the plan — that check is the
  server-side `verify` above.

**Tests added:** `functions/ai/dates.test.js` (timezone boundaries, DST-free offset math,
half-hour zones, hostile offsets), gateway tests for the CONTEXT block and the prompt
contract, tool tests for date/provenance/field-order/registry, mutation-flow tests for the
hallucinated id, the missing plan and the changed-after-proposal case, `dietEntries` rule
tests, Dart tests for the estimation helpers and two widget tests pinning the "~" to
estimated plans only.

**Deploy required (owner creds):** `firebase deploy --only functions,firestore:rules`.
Ship the client and the rules together — the tightened `dietEntries` rule rejects writes
from app builds that predate it.

## Phase 1 — what actually landed (2026-08-30)

The spine the coach was missing. ZIVO now knows what the user is trying to do — and,
just as importantly, knows when it *doesn't*.

- **The objective is a first-class entity.** `DietGoal` (fat loss · maintain · muscle gain ·
  recomp) and `NutritionTargets` (kcal + optional per-macro grams) with a `TargetSource`
  recording where the numbers came from — `manual`, `calculated`, or `planDerived`. Stored at
  `users/{uid}/dietTargets/current` behind a new rule and rule tests; read through
  `DietRepository.watchTargets` / `saveTargets` / `clearTargets` in both implementations.
- **Null is a real state, and stays one.** There is no default target and nothing derives one
  automatically. Unset means the Diet hero counts down the day's plan under the label
  `KCAL LEFT OF PLAN`, Today's glance says "of plan", the target card says "No daily target
  set", and the coach is handed `targets: null` with instructions to say so. An unrequested
  target the user never approved would be the same trust failure as an invented calorie.
- **The screen measures the objective.** With a target set, the hero ring counts down
  *that* target (`KCAL LEFT`, or `KCAL OVER` — over-target is a state a coach has to be able
  to name, so it is never clamped), the macro bars use the user's own macro targets and a
  macro with no target simply gets no bar, and the header names both figures separately:
  `TARGET 2200 KCAL · PLANNED ~1270 KCAL`. Two numbers are fine when they are labelled
  differently; two unlabelled ones are not.
- **Provenance again.** The summary row under the hero states the goal and where the number
  came from ("You set this" / "Calculated from your body data"). The calculator
  (Mifflin-St Jeor + activity factor + a goal adjustment, pure and on-device) *fills the
  fields* as a proposal and shows its working — "1780 at rest, 2136 to maintain, adjusted for
  fat loss". Nothing is written until Save. Editing a calculated figure by hand demotes it to
  `manual` and drops the basis, because the stored explanation would otherwise be a lie.
- **A deterministic safety floor.** `kMinimumSafeCalories` (1200) is checked in pure code, not
  left to the model to notice: below it the target editor shows an explicit warning
  recommending a doctor or registered dietitian, and the Diet screen keeps saying so. The
  number is never silently clamped — clamping would hide that the inputs and the goal don't
  add up to something ZIVO should be coaching.
- **The coach gets all of it.** `get_diet` and `get_today` now carry `targets` and a
  server-computed `remaining` (per macro, `null` where no target was set — "you didn't set a
  carb target" and "you have 0g left" are opposite statements). The prompt gained rules
  separating the user's objective from a plan day's sum, telling it to lead with the goal, and
  spelling out that `remaining` is derived from **ticked meals, not a food log** — the honest
  caveat until Phase 3.
- **One fix in passing:** `_PlanBody` was re-creating the consumption stream on every rebuild;
  it now owns it in state, so the extra rebuild the targets stream causes can't tear down and
  re-open the subscription (which also blanked the hero's numbers mid-session).

**Tests added:** `test/diet/diet_targets_test.dart` (goal/source parsing never defaulting,
Mifflin-St Jeor against published values, determinism, macros summing back to the calorie
figure, the safety floor, no negative carbs, `buildTargetProgress` including over-target and
untracked-macro cases, repository round-trip), `test/diet/diet_targets_page_test.dart` (nothing
saves without Save, blank macro saves null not zero, the low-calorie warning, the calculator as
a proposal, hand-editing demoting the source, removal), four Diet-screen widget tests, two
Today-glance tests, five `dietTargets` rule tests, and five tool tests plus two prompt-contract
tests on the server.

**Deploy required (owner creds):** unchanged from Phase 0 —
`firebase deploy --only functions,firestore:rules`, shipped together with the client build.

## Phase 2 — what actually landed (2026-08-30)

The missing dependency. ZIVO can now answer "what is 200 g of chicken breast
worth" from a verified record instead of a model — and, just as importantly, can
say when it can't.

- **A real catalog, mechanically derived.** `assets/nutrition/foods.json` — 7,308
  foods (1.0 MB) built by `scripts/nutrition/build_food_db.js` from USDA
  FoodData Central's Foundation Foods (2026-04-30) and SR Legacy (2018-04)
  exports, both public domain. Every row carries the real `fdcId` it came from,
  so any number on screen is traceable to a specific USDA record. **Nothing in
  the catalog was hand-written or model-generated** — a hand-authored catalog
  would have reproduced T1 one layer down, wearing a USDA badge.
  Rows that don't state all four macros, or whose macros contradict their stated
  energy beyond a generous 4/4/9 tolerance, are dropped rather than stored with
  holes.
- **Three outcomes, not one.** `FoodMatch` is a sealed set — `FoodResolved`,
  `FoodAmbiguous`, `FoodNotFound` — so there is no way to consume a lookup
  without deciding what to do when the food is uncertain or absent. This is what
  makes requirement 8 structural instead of aspirational.
- **Raw vs cooked is a first-class dimension.** Preparation is derived from
  USDA's own description and preserved as `unknown` when it can't be told. A
  query matching both forms of a food resolves to `FoodAmbiguous` when their
  energy differs materially (>25%) — raw rice is 365 kcal/100 g and cooked is
  130, so "100 g rice" is a ~3× fork and must become a question, exactly the
  clarification the original brief asked for. When close matches *agree* on the
  numbers, it resolves silently; asking when the answer doesn't change anything
  is noise, not rigour.
- **The calculator is the only path from food to calories.** `nutritionFor` is
  pure, deterministic and total: it returns either a `ResolvedNutrition` that
  carries its own `source`/`sourceRef`, or a `QuantityUnresolved` saying why.
  Mass units convert exactly; **volumes are refused** unless the source recorded
  that measure for that exact food, because "100 ml of olive oil is 100 g" is
  wrong by ~8% and for flour by a third. The refusal names the measures that
  would work.
- **One catalog, two runtimes, provably identical.** The build script writes the
  asset twice — the app bundle and `functions/nutrition/foods.json` — and
  `functions/nutrition/food_db.js` mirrors the Dart resolver and calculator.
  `test/fixtures/nutrition_vectors.json` holds 8 lookups and 10 computations run
  by **both** `flutter test` and `node --test`, plus a catalog checksum. Change
  one implementation, or rebuild the catalog without regenerating the vectors,
  and the other side fails. That is the intended friction, and it is the real
  answer to two-implementations drift.
- **Wired but not yet used by a screen.** `AppScope.foods` exposes the resolver
  (lazily loaded — a session that never looks a food up never parses the asset).
  The surfaces that consume it are Phase 3's: a food log, and the "not found →
  define your own food" path that the USDA-only decision makes necessary.

**Known limits, stated rather than hidden:** coverage is US-shaped, so
`FoodNotFound` is common for regional cooking — the agreed answer is user-defined
custom foods in Phase 3, not a hand-curated regional supplement. SR Legacy is a
2018 snapshot and includes some branded products whose recipes have since
changed; ranking prefers the plainer generic records.

**Tests added:** `test/diet/food_resolver_test.dart` (16 — real-catalog
provenance, published USDA values, the raw/cooked fork, no partial-match drift,
exact unit conversion, the density refusal, determinism),
`test/diet/nutrition_vectors_test.dart` and `functions/nutrition/food_db.test.js`
(the shared vectors, the catalog checksum, and the app/server byte-identity
check).

**Deploy:** unchanged — `firebase deploy --only functions,firestore:rules`. Note
the functions bundle now carries the 1 MB catalog.

## Phase 3 — what actually landed (2026-08-30)

Consumption stopped being an assumption. "I ate two eggs and 100 g of rice" is
now representable, and every figure derived from it is traceable.

- **`FoodLogEntry` is the ledger.** One row per thing eaten, carrying the food
  reference (`foodId` + `sourceRef`), the quantity as given, the mass it
  resolved to, and the nutrition computed at log time. The figures are **stored,
  not recomputed on read**: the catalog can be rebuilt, and a past day must not
  silently change its totals when it is. Persisted at `users/{uid}/foodLogs`
  with a tight rule and six rule tests.
- **`origin` keeps two different claims apart.** `logged` means the user
  recorded it; `plannedMeal` means the app materialised it from a ticked meal.
  "You ate 1,850 kcal" and "your plan values what you ticked at 1,850" are not
  the same statement, and every layer — totals, `TargetProgress`, the tool
  payload, the prompt — can now tell which one it is holding.
- **Ticking a meal still works, and now means something.** The interaction is
  unchanged; underneath it writes `dietEntries` (the tick state, untouched, so
  older builds keep working) **and** one `foodLogs` entry per planned item,
  tagged `source: dietPlan` with the item's `estimated` flag riding along rather
  than being laundered into a measurement. Un-ticking removes exactly those
  entries and never the user's own. Removing one item of a ticked meal leaves it
  ticked — that is what a half-eaten meal looks like — and removing the last one
  un-ticks it.
- **The fallback is explicit.** `buildTargetProgress` sums the log when the day
  has one, and falls back to the planned figures of ticked meals only when it
  doesn't (days recorded before the log existed), reporting which through
  `consumedIsFromTickedMeals`. Server-side the same three cases surface as
  `consumed.basis`: *logged by the user* / *materialised from ticked plan meals,
  not weighed* / *nothing logged* — and the prompt now requires the coach to
  read it before characterising any total. **An empty log means nothing was
  recorded, not that nothing was eaten**, which is the difference between a
  coach that helps and one that tells you to eat when you already have.
- **Custom foods close the USDA gap.** `CustomFood` + `CompositeFoodResolver`
  layer the user's own foods over the reference catalog, so their "Koshari"
  beats anything USDA loosely matches and is labelled `userCustom` wherever it
  surfaces. The logging sheet's not-found state offers to define the food rather
  than approximating it. A deleted custom food resolves to null, never a
  lookalike — substituting would silently rewrite what a past entry meant.
- **The logging UI refuses what it can't compute.** Search → pick → amount, with
  a live preview computed by `nutritionFor`. Only the measures the source
  recorded for that exact food are offered (no generic "cup"), and an amount it
  can't resolve shows the reason and the measures that would work instead of a
  number.
- **One durable fix in passing:** `test/support/diet_repository_stub.dart`, so
  the next repository addition doesn't break every hand-written fake in the
  suite and surface as a failure in an unrelated file.

**Tests added:** `test/diet/food_log_test.dart` (20 — totals and the assumed-day
flag, planned-meal materialisation and its provenance, the tick/un-tick/partial
cases, log-wins-over-plan, the explicit fallback, the composite resolver),
`test/diet/log_food_sheet_test.dart` (4 — the full logging flow, the refused
unit, the not-found → define-your-own path, provenance on the Diet screen), four
new tool tests for the three kinds of day, two prompt-contract tests, and ten
`foodLogs`/`customFoods` rule tests.

**Deploy:** unchanged — `firebase deploy --only functions,firestore:rules`. The
new `foodLogs` and `customFoods` rules must land before either can be written.

## Phase 4 — what actually landed (2026-08-30)

One structured picture, built once, rendered by the screen and read by the coach.

- **`DietState` is the object.** Goal · targets · consumed (with its
  `ConsumedBasis`) · remaining · meals · the plan's own daily sum, reported
  separately · a week of history · and a `DietQuality` block naming what the app
  does *not* know (`targetsUnset`, `noPlanForDay`, `nothingLogged`,
  `consumedIsAssumed`, `hasEstimatedValues`, `untrackedMacros`). It answers the
  audit's seven questions *in code* rather than in prose.
- **`buildDietState` is pure and total.** No clock, no repository, no network —
  every input is passed in, so the same inputs always give the same state. It is
  the single place the ordering rules live: supplements never count, the log
  beats the plan when it has anything, a missing target is null rather than
  zero, and an empty log is "nothing recorded" rather than a measured zero.
- **The two implementations are now pinned, not merely parallel.**
  `functions/diet/state.js` mirrors the Dart builder, and
  `test/fixtures/diet_state_vectors.json` — **10 state cases and 28 day
  resolutions**, covering all seven weekdays against per-weekday, every-day,
  single-day and ambiguous plans — is run by **both** `flutter test` and
  `node --test`. Change one side and the other fails until they agree. That
  closes the half of T13 Phase 2 left open: `dayForDate` and `resolveDietDay`
  are now provably the same rule.
- **Wired, not just written.** The Diet hero, Today's glance and both diet tools
  all build a `DietState` — the tool payload *is* the state, projected in an
  order where truncation eats the plan's items rather than the user's position.
  Phase 1's `TargetProgress` was the stopgap this replaces and has been
  **deleted**: keeping both would have been the two-implementations problem in
  miniature.
- **`get_today` gained a week of history in one read.** `dayKey` is a sortable
  string, so a range query covers seven days without a composite index or seven
  round-trips. The average covers only days that had something recorded —
  averaging zeros for unlogged days would invent a trend out of missing data.
- **The prompt now reads `quality`.** It is told what the app doesn't know
  rather than left to infer it, told that a macro in `untrackedMacros` has no
  target so it must not call the user "over" or "under" on it, and told plainly
  that the payload is the same state the screen renders — so a claim the screen
  would contradict means it misread the state.

**Tests added:** `test/diet/diet_state_test.dart` and
`functions/diet/state.test.js` (the shared vectors both ways, plus the rules the
state enforces in one place), and one prompt-contract test. The existing tool
tests were rewritten against the state-shaped payload.

**Deploy:** unchanged — `firebase deploy --only functions,firestore:rules`.

## Phase 5 — what actually landed (2026-08-30)

The coach's decisions are code now. The model's job is delivery.

- **`CoachingFinding` types the six registers** the brief asked for —
  observation · analysis · recommendation · warning · encouragement ·
  clarification — each with a severity, a **deterministic sentence that is
  correct on its own**, and an `evidence` list naming the `DietState` fields it
  was derived from. That evidence list is what makes "why is this being said?"
  answerable rather than asserted, and the deterministic text is what Phase 7's
  validator will fall back to when it rejects a generated reply.
- **`coachingFindings` is pure: state in, at most three findings out.** Three,
  because a coach who lists six things has told you nothing. Ranked by
  severity, stably, so the same state always yields the same three.
- **The rules fire only when they have something real to say**, and the tests
  assert the silence as hard as the speech: a met protein target produces
  encouragement and *no* shortfall; a protein gap at 09:00 stays quiet because
  there is a whole day to close it; the same gap at 19:00 with the budget
  running out becomes the brief's worked example, complete with the room it has
  to work within — *"35g short of the 160g protein target, with 350 kcal left"*.
  An empty day produces no overshoot, and an empty log is **never** rendered as
  "you haven't eaten".
- **Time is an input to the rules, not a field on the state.** `localHour` is a
  property of *now*, not of the day being summarised, so it's a parameter — and
  when it's unknown, time-sensitive rules simply don't fire. A coach that
  doesn't know whether it's breakfast or bedtime should say less, not guess.
  Asking about a past day correctly gets no evening nudge.
- **One ranking decision worth recording:** the provenance clarifications
  (*these totals are assumptions*, *these figures were estimated*) were
  initially `info` and got crowded out of the cap by plain readouts. They're
  `notable` now. Being wrong about what a figure MEANS is worse than omitting
  the figure.
- **Wired, not shelved.** The diet tool payload carries `findings` alongside
  the state, and the prompt now says plainly: lead with them, never contradict
  one, never invent a recommendation they don't contain, don't soften a
  warning, and pass a clarification on as the gap it describes. New coaching
  behaviour belongs in the engine — the prompt is delivery, not policy.

**Tests added:** `test/diet/coaching_rules_test.dart` and
`functions/diet/rules.test.js` (the shared vectors both ways, the cap, the
evidence requirement, and eight explicit negatives), two tool-level tests, and
one prompt-contract test. Shared fixture:
`test/fixtures/coaching_vectors.json`, 11 cases.

**Deploy:** unchanged — `firebase deploy --only functions,firestore:rules`.
