# ADR-007: Diet onboarding — body data, the plan verdict, and generated plans

## Context

Diet answers "what does my plan say" and "did I eat it". It cannot answer the two
questions a person actually arrives with:

1. **"I already have a diet — what is it doing to me?"** ZIVO can import a plan and total
   it up, but it has never been able to say *gaining* or *losing*, because it has no
   picture of the body the plan is being eaten by. The screen just counts down the plan's
   own total and nags "No daily target set", which is a demand, not an answer.
2. **"I don't have a diet — build me one."** There is no generator at all. Import or hand-type
   are the only ways a plan exists.

Both were reported by the owner from the live app, alongside a third gap: a plan can only be
captured from a **file**, and only one plan can exist at a time.

The constraint that makes this non-trivial is the standing rule from the coach audit:
**ZIVO never invents a number.** A calorie enters through `FoodResolver` or not at all;
`NutritionTargets` is null until the user sets one, and no target may be auto-derived from
body weight on first run. Anything built here has to answer both questions without
breaking that.

## Decision

### 1. Body data becomes a stored entity — but it still buys nothing on its own

`BodyProfile` (height · sex · activity · optionally the user's own known maintenance
figure) is persisted at `users/{uid}/bodyProfile/current`. It was previously ephemeral,
living only inside a calculated target's `TargetBasis` on the theory that it is "an input
to an equation, not a profile field". Two independent features now need it (target
calculation *and* the plan verdict), and asking twice for the same numbers is worse than
storing them once.

**Weight is not part of it.** Weight already exists as a time series in the workout
feature's `BodyWeightRepository`, and it is the one number here that legitimately changes
week to week. `BodyProfile` deliberately has no weight field, so the two can't disagree;
the verdict reads the latest weigh-in and says how old it is.

**Age is not part of it either** — it is derived from `UserProfile.dateOfBirth` at call
time. A stored integer age is wrong within a year of being written.

Storing body data is **not** the same as deriving a target from it. Nothing here writes
a target. The rule the audit set stands unchanged: a target appears when the user approves
one.

### 2. The verdict is deterministic, not a model call

`analysePlan(plan, measures)` in `domain/analysis/plan_verdict.dart` is pure: the plan's
average daily calories (supplement meals excluded) measured against maintenance
(Mifflin-St Jeor × activity, or the user's own stated figure when they gave one), yielding
a direction, a kcal/day delta and a projected kg/week at 7,700 kcal ≈ 1 kg.

This follows the precedent `domain/coaching/rules.dart` set and for the same reason: **the
model phrases findings, it does not decide them.** A verdict that depended on a model call
would be non-reproducible, unavailable offline, and impossible to pin with vectors — and
it would be free to say "you'll gain" about arithmetic it never did.

Two honesty properties are load-bearing:

- **A deadband.** Inside ±100 kcal/day the verdict is `holding`, not a tiny gain. A
  population BMR equation carries more error than that, and a projection of "+0.02 kg/week"
  claims a precision the inputs cannot support.
- **The verdict inherits `estimated`.** An imported plan's calories were generated by a
  model (see FEATURE.md); a verdict resting on them is marked "~" exactly as the totals are.

### 3. Generated plans are priced by the catalog, not by the model

`aiGenerateDietPlan` asks the model for foods, portions and meal structure from the user's
preferences and target — and then **prices every item server-side through
`functions/nutrition/resolve.js`**, the same USDA mirror the coach's `resolve_food` tool
uses. A deterministic scaler nudges portions so the day lands on the target. Items the
catalog cannot resolve (koshari, ful, baladi bread — USDA covers regional cooking poorly)
keep a model estimate and are marked `estimated`, the same fallback imports already use.

The alternative — letting the model return the numbers, as `diet_import.js` does — was
rejected for *generated* plans specifically. An imported plan's figures come from a
document a human authored and the user already trusts; ZIVO is transcribing. A generated
plan's figures would be ZIVO's own claim, and inventing those is the exact failure the
audit's whole design exists to prevent. Refusing every unresolvable food was also rejected:
it would produce plans with no Egyptian food in them.

Generated output lands in the **existing review editor** and is saved only by the user, on
the same footing as an import.

### 4. Plans become a library

`DietRepository` gains `watchPlans` / `setActivePlan` / `archivePlan`; `activePlan` remains
as the single active plan the whole app reads, now derived from `status` rather than from
there being only one document. `DietPlanStatus` already models `draft`/`active`/`archived`,
so this is a repository and rules change, not a model one.

### 5. One capture path, four sources

PDF, photo, **dictation** and typing all land in one extractor and one review screen.
Photo already works (the picker takes images; only the entry point's name says "PDF").
Dictation reuses the Ask feature's recorder and transcription, then feeds the transcript to
the same extractor as text. Four entry points, one pipeline — the alternative is four
schemas that drift.

## Consequences

- Body data is now **asked for up front** during diet onboarding rather than hidden behind
  a calculator sheet in the targets screen. That is a deliberate reversal of "don't ask for
  what you don't need yet": the verdict is the feature, and it is unavailable without it.
- The "No daily target set" empty state gains two one-tap answers (adopt the plan's own
  total → `TargetSource.planDerived`, or calculate from body data → `calculated`). Both
  still require an explicit approval; neither writes on its own.
- `DietState` grows the verdict, so Today's glance and the coach get it for free — and a new
  coaching rule can fire on "your plan and your goal disagree".
- A new Firestore collection (`bodyProfile`) needs a rule **and** a rule test.
- `aiGenerateDietPlan` is a `functions` deploy — an owner action, not something an agent runs.
- Storing body data raises the sensitivity of the account's data slightly; it stays
  owner-scoped and deny-by-default like everything else, and account deletion already wipes
  `users/{uid}` server-side.
